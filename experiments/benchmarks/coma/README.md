Хотим проверить, как зависит качество генерации массингов через влм в соответствии с контекстом от форматов подачи контекста на обучении и инференсе.
Массинг представляется в виде json, контекст это набор массингов.
Под форматом подачи контекста подразумевается то, в какой вид мы преобразовываем контекст перед подачей его в влм.
Зафиксируем, что такое соответствие контексту абстрактно.
Соответствовать контексту - значит вести себя так же, как реальные здания ведут себя в реальном контексте. То есть "здание соответствует контексту" = "здание ведет себя так же, как реальное здание в этом контексте". При этом мы подразумеваем, что геометрия здания неким образом зависит от контекста, иначе такой замер соответствия не имел бы смысла.
Зафиксируем, что значит соответствие контексту на практике.
Мы не знаем наверняка, каким образом геометрия массинга зависит от контекста. Однако метрика оценки контекста по сути является бинарным классификатором - является ли массинг истинным для этого контекста или нет. И ее можно развернуть в обратную сторону - проверять, является ли контекст истинным для массинга. Соответственно, если метрика будет чувствительна к изменению контекста, значит она кодирует верную зависимость массинга от контекста и ее можно использовать.

Что нужно сделать:
- подготовить данные - реальные пары массинг-контекст с контекстом в разных форматах, разделить на трейн и тест случайным образом
- обучить влм на разных форматах контекста
- заинференсить разные чекпоинты влм на разных форматах контекста
- измерить чувствительность метрики к контексту на всем датасете
- замерить метрики на разных сабмитах влм
- проинтерпретировать результаты

Все метрики вычисляются по такой схеме:
Е = exp(-|gen_massing_value - reduction(context_values)| / (context_values_std + small_constant)), где
reduction = mean, nearest (берем ближайшее значение к get_massing_value)
gen_massing_value/context_values - некие численные характеристики массинга (сгенерированного и массингов из контекста).

Оценивать метрики будем методами оценки бинарной классификации: ROC-AUC, Recall@k, F1-Score. При этом датасет для оценки метрики будет строиться следующим образом - берем весь датасет CoMa, для каждого сэмпла делаем негативный пример, случайным образом подмешивая туда чужой контекст, получаем тем самым удвоенный датасет с одинаковым количеством positive и negative сэмплов.

Как работать с кодом:

Идейно репозиторий устроен следующим образом: в src лежат файлы с классами, в experiments мы эти классы импортируем в конфигах и запускаем. При этом в src есть файлы в папках и просто файлы - в папках лежат файлы с классами, которые имеют общий интерфейс (т.е. в папке лежит файл с абстрактным классом и файлы с классами-наследниками), а просто файлы - это классы, которые единого интерфейса не имеют. Соответственно, в части метрик:
- пайплайны работы с метриками будут лежат в папке experiments/benchmarks/coma
- внутри есть две папки - в одной пайплайн для оценки самих метрик, в другой пайплайн для оценки модели на этих метриках

Разберем, как работать с метриками на примере пайплайна их оценки:
Пайплайн валидации метрик задается конфигом experiments/benchmarks/coma/metrics_validation/validation_config.json. Он представляет из себя инициализацию класса Validator (по сути аргументы его __init__ метода), где в аргументы тоже могут подаваться классы, и тогда их инициализация записывается аналогично. Validator делает следующее - берет некий датасет, метрики, и запуская его метод __call__ мы замеряем метрики на этом датасете. 
При этом наши метрики - по сути бинарные классификаторы, которые определяют, является ли массинг истинным для контекста. А при оценке валидности метрик мы их инвертируем - хотим понять, насколько метрика отличает истинный контекст от ложного. Поэтому Validator замеряет качество классификации "истинности" контекста нашими метриками на датасете с истинным и ложным контекстом.
При этом качество классификации замеряется типовыми метриками вроде ROC-AUC. Эта часть кода уже реализована - в Validator подается как метрика класс SampleMetricROCAUC (наследуется от интерфейса Metric), метод __call__ которого делает следующее - принимает датасет, где есть массинг, контекст, и метка истинности этой пары, применяет к каждому примеру нашу метрику-классификатор и считает ROC-AUC. 
Соответственно, теперь нам необходимо имплементировать сами метрики - класс, __call__ метод которого будет применяться к каждому примеру датасета. Для таких классов есть общий интерфейс SampleMetric, он и всего его наследники лежат в папке src/sample_metric. При этом заметим, что все метрики, которые мы предлагаем, считаются по общей схеме - мы берем некоторую численную характеристику массинга, применяем ее к сгенерированному массингу и всем массингам из контекста, и считаем значение метрики по формуле (см. выше, формула для Е). Для удобства этот код тоже уже реализован - есть класс MassingContextualRelevance, который содержит в себе эту формулу. Этот класс при инициализации принимает в себя другой класс, который как раз считает численные характеристики массингов - он тоже наследует SampleMetric, и именно эти классы для подсчета численных характеристик нам и предстоит имплементировать.
Соответственно, чтобы имплементировать класс для подсчета численной характеристики массинга, необходимо сделать следующее:
1. В папке src/sample_metric создать файлик, назвать как свой класс, но в lowercase
2. В файлике создать класс, наследованный от SampleMetric. Тут по аналогии с другими файлами в этой папке: можно скопировать код из любого, поменять название класса, поменять тело __call__, имплементировать __init__ (тоже по аналогии, с аннотациями, можно пройтись по файлам и посмотреть, как реализовано)
3. В __init__.py (тоже лежит внутри src/sample_metric) импортировать из этого файла

Часть метрик уже имплементирована (выше в списке метрик через тире указаны ключи этих метрик из конфига), на их примере можно посмотреть, как все устроено. Некоторые метрики используют вспомогательные классы, которые инкапсулируют некую общую логику - например, чтобы считать некие оценки над полигонами внутри массинга, есть метрика MassingPolygonsMetric, которая берет класс с интерфейсом PolygonsAnalyzer (src/polygons_analyzer), который считает некую характеристику полигона, и применяет его ко всем полигонам массинга, поэтому чтобы сделать новую метрику для оценки полигонального свойства массинга, можно имплементировать класс типа PolygonsAnalyzer и применить его внутри метрики MassingPolygonsMetric. В целом может быть полезно посмотреть классы в src/sample_metric, возможно какую то общую логику можно переиспользовать в своих метриках.

При этом feel free имплементировать другие метрики оценки бинарной классификации для проверки метрик. Это можно сделать аналогично SampleMetricROCAUC - создать новый класс в папке src/metric.

В файле experiments/benchmarks/coma/sample.json лежит пример json представления массинга - именно с ним работают метрики.
